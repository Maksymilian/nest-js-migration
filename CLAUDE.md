# CLAUDE.md

## Domain-Driven Design: stick to the ubiquitous language, the context boundaries and the tactical rules

The architecture is in `docs/architecture.md` (section 3 has the tactical rules) and the vocabulary in `docs/ubiquitous-language.md`. Read both before changing domain code. For aggregate, event, repository and integration decisions, also apply the `implementing-domain-driven-design` skill.

**Strategic**
- **IMPORTANT: Use only terms from `docs/ubiquitous-language.md`** in class, method, variable, REST path, GraphQL type and field, table, event and test names, and in docs and commit messages. Never use the words in its "Don't say" column (for example `user`, `device`, `update`/`edit` for a correction, `delete` for a void). Terms belong to their context: an upstream *correction* is a *revision* in Training Progress. If a concept has no term yet, propose one and add it to the glossary in the same change, instead of inventing a name in code.
- **Subdomains decide the effort:** Training Progress is the core domain (rich model, most care); Workout Tracking and Billing are supporting (keep it simple, no ceremony; Billing since ADR 2); Notifications, Calendar, Identity and Payments are generic: use a library or provider (`@nestjs/mail`, `date-fns`, an identity provider, Stripe behind Billing's anticorruption layer) behind a port, never a hand-built model.
- **Each core or supporting context has its own service and database.** A service never reads another service's database and never calls another service synchronously. A generic context may run as a module inside a service, but it's still a separate context.
- **Only integration events cross a context boundary**, in the upstream's published language (`libs/workout-tracking-contracts`, `libs/billing-contracts`, `training-progress/published-language/`). The downstream translates them in its anticorruption layer; contract classes never reach a domain model. No domain classes in `libs/` (`libs/ddd` is technical building blocks only).

**Tactical**
- **Aggregates:** small, around true invariants; one root; intention-revealing methods named in the language, no setters; references to other aggregates by id only, never another aggregate as a method argument; optimistic locking via a `version`/`revision` column; ids generated by the domain.
- **Strict aggregate isolation:** ids and value objects go in the module's `domain/values/`, the only part of a module's domain another module's domain may import. Roots, entities, repositories, domain events and domain errors are private to their module. Only a factory method that creates another aggregate (`equipment.recordWorkout()`) may import that aggregate's root, and only if it's declared in `.dependency-cruiser.cjs` and `docs/architecture.md` section 11.1. `application/` may coordinate several aggregates of its own context.
- **One aggregate per transaction.** Cross-aggregate consistency is eventual: a domain event, then a policy that changes one aggregate per transaction.
- **Domain events** are meaningful business facts in the past tense, raised by aggregates, and written to the outbox (`@nestjs/outbox`) through `DomainEventPublisher` **in the same transaction** as the aggregate. Never publish from memory (no `EventBus`, `EventEmitter2` or `ClientProxy.emit()` for domain or integration events). No events for property changes or technical signals.
- **Every handler is idempotent:** the inbox in the same transaction (`processInTransaction`), or a state guard in the aggregate.
- **No scheduled jobs:** these are microservices, so no `@nestjs/schedule` cron, interval or timeout jobs, and no cleanup of the outbox or the inboxes, without the user's approval first. A stale or stuck message is an incident: it's found through observability and resolved then, not swept up by a job. Time-based work is a schedule trigger instead: a Kubernetes CronJob runs `scripts/scheduler/publish-schedule-trigger.mjs`, which publishes a CloudEvent to the service's schedule queue, and the one instance that receives it handles it idempotently (`docs/architecture.md` section 7.5). The same script runs it by hand.
- **Value objects** for ids, quantities and periods: immutable, validated at construction, compared by value. Entities only where identity and lifecycle matter.
- **Repositories** only for aggregate roots, defined in `domain/` as ports, returning aggregates, holding no business rules. Queries bypass the domain model and read SQL into read models.
- **Layers:** `domain/` imports nothing from NestJS, Drizzle, `@nestjs/outbox` or other layers (pure libraries such as `date-fns` and `libs/ddd` are allowed); `application/` holds thin use cases and policies (load, call one method, save, stage events) and owns the transaction; `infrastructure/` implements ports; `interface/` (controllers, resolvers, message handlers) only validates input and dispatches commands or queries. Technical plumbing goes in `platform/`, never domain concepts.
- **Boundaries are checked at build time:** `pnpm check:architecture` (dependency-cruiser, `.dependency-cruiser.cjs`, rules in `docs/architecture.md` section 11.1) runs in `pnpm lint`, before `nest build` and in CI. TypeScript enforces apps → libs too: each library's `tsconfig.lib.json` has `rootDir: ./src`, so a library importing an app or another library fails `pnpm typecheck` (in `pnpm lint`); keep it that way for new libraries. Run it after every change that adds an import. **Never weaken, skip or add an exception to a rule to make an import pass; change the design.** A new exception needs the user's approval first. Import libraries only through `@app/<lib>`, never a deep path.
- **Not used, on purpose:** a Shared Kernel, a package per bounded context (workspace packages with `exports`), TypeScript project references and tsconfig `paths` beyond what `nest generate app|library` adds. Contexts are Nest apps and `libs/` in Nest CLI monorepo mode.
- Business rules live in aggregates and value objects; DTOs only check the shape of input.
- **Observability is OpenTelemetry only** (`@app/telemetry`, `docs/architecture.md` section 15): no vendor SDK in the services; Grafana Alloy collects everything (and scrapes RabbitMQ and Valkey), Tempo, Loki and Prometheus store it, Grafana shows it. Every outbox message carries the trace (`traceHeaders()` in the publishers), in-process handlers use `@OnTracedOutboxMessage()` instead of `@OnOutboxMessage()`, and a broker transport is wrapped in `TracedTransport()`. A member's interaction is a *flow* (`session.id` baggage). Telemetry only travels authenticated: Basic Auth at minimum on Alloy (TLS outside the local machine); never publish Loki's, Tempo's or Prometheus' ports. Log destinations are configuration, not code: `LOG_CONSOLE`, `OTEL_*_EXPORTER=none`, and Alloy's config. Dashboards and alert rules are provisioned from `infrastructure/grafana/`: change them there, not in Grafana.
- **Tests:** aggregates as given/when/then on the domain events they raise and the errors they throw; policies and the anticorruption layer for idempotency and ordering.

## Database, infrastructure and checks

- **Schema changes go through Liquibase only.** Add a new formatted-SQL changeset in `apps/<service>/liquibase/changesets/` and include it in `changelog.yaml`; never edit an applied changeset. Keep the Drizzle schema in `platform/database/schema.ts` (used only to build queries) in step with it. Test records go in `liquibase/test-data/` with `context:test-data`. The outbox's `nest_outbox` schema is a changeset too (from `pnpm exec nest-outbox sql`, the store runs with `migrate: false`): upgrading `@nestjs/outbox` means a new changeset with `--from`.
- **The changesets that exist now are the production baseline:** Workout Tracking's `0001`–`0002`, Training Progress' `0001`–`0003`, and those two services' `test-data/0001`. Billing's changesets and Training Progress' `0004` and `test-data/0002` are new, not in production yet. Never edit, renumber or squash them; every later change is a new changeset on top.
- **Every changeset has a hand-written `--rollback`, used to revert it in production** (Liquibase can't generate one for formatted SQL). It undoes exactly that changeset and leaves the schema as it was before: one `--rollback` line per statement, in reverse order. That includes test records (delete the rows inserted) and outbox upgrades. When the change loses data (dropping a column or table, narrowing a type), the rollback can only bring back the structure: say so in the changeset's `--comment`, and prefer splitting it into an additive changeset now and the removal in a later release. A changeset that can't be reverted needs the user's approval first. Tag and revert with the scripts in `scripts/database/` (Liquibase Open Source 4.33 in Docker, nothing to install; without `--url` and `--username` they target the local Docker Compose database): `tag.sh <service> <release>` on every database before each release; `rollback.sh <service> --tag <release>` prints the rollback SQL, `--apply` runs it after a confirmation, and `--label <ticket>` limits it to the changesets carrying that label; `liquibase.sh <service> <command>` runs any other command (`history`, `status`). Roll back from a checkout of the release being reverted (Liquibase reads the rollback SQL from the changelog), then deploy the application version that matches the reverted schema.
- **Infrastructure runs in Docker Compose** (`docker compose up -d --wait`): PostgreSQL x3, Valkey and RabbitMQ; the Stripe CLI in the `stripe` profile. Liquibase isn't part of it: migrate the local databases with `scripts/database/liquibase.sh <service> update`. RabbitMQ topology lives in `infrastructure/rabbitmq/definitions.json` and in the service that declares it, with the same arguments, or RabbitMQ refuses the redeclaration.
- **Until Identity exists, a member id is the member's email address**, not verified: DTOs and GraphQL args check it with `@IsEmail()`; the domain's `MemberId` stays an opaque string.
- **Before calling a change done:** `pnpm test`, `pnpm test:e2e` (each service on its own PostgreSQL in Docker, via Testcontainers, with its Liquibase changesets), `pnpm lint` (oxlint, the type check and the architecture check) and `pnpm build`. When a changeset is added, test its rollback on the local database with `scripts/database/liquibase.sh <service> update-testing-rollback` (it applies the pending changesets, rolls them back and applies them again). When an API changes, update its Postman collection in `postman/` and run it with `pnpm dlx newman run`.
- **Stress, spike and soak tests after every major refactoring**, especially a change of database driver or ORM, of the main framework (NestJS, its HTTP adapter, the GraphQL driver), or adding, changing or removing infrastructure (PostgreSQL, Valkey, RabbitMQ, the observability stack, Docker Compose, Kubernetes). Once the checks above pass, ask to run the k6 load tests (`load-tests/k6.sh stress` and `spike`, `docs/architecture.md` section 17), run them, and report p95 and p99 latency, errors, throughput and the alerts that fired, compared with the previous run. Such a change isn't done until both have run; if a run is declined, say which. There's no soak test yet: once `load-tests/soak.ts` exists, run it too and also report memory, connections and queue depth over time (leaks).

## Main documentation: NestJS docs

**The NestJS documentation at https://docs.nestjs.com is the main reference for this project.** Check it before designing or implementing any feature.

- **Local cache:** `docs/nestjs/` holds the Markdown source of the site (from the `content/` folder of https://github.com/nestjs/docs.nestjs.com). Read and grep it first instead of fetching the website. `docs/nestjs/SOURCE.md` records the commit and date of the last sync.
- **Syncing:** when asked to "sync the docs", run `scripts/sync-nest-docs.sh`. Never edit files in `docs/nestjs/` by hand.
- If the cache and the website disagree, the website is newer. Mention it and suggest a sync.

## Always prefer recipes and official libraries

**IMPORTANT: Before writing custom code, check whether the docs already provide a recipe or an official/recommended library for the problem, and use it.** Only write a custom solution when nothing in the docs fits, and say why.

Where to look in `docs/nestjs/`:

| Need | Folder |
|---|---|
| Recipes (Passport, CQRS, CRUD generator, REPL, router module, serve static, SWC, hot reload, AsyncLocalStorage, nest-commander) | `recipes/` |
| Configuration, validation, logging, queues, task scheduling, events, HTTP client, serialization, file storage, mail, i18n | `application/` |
| Databases and ORMs (TypeORM, Prisma, Drizzle, MikroORM, Mongo, Sequelize, caching) | `data/` |
| Authentication, authorization, CORS, CSRF, Helmet, rate limiting, hashing | `security/` |
| Health checks (Terminus), resilience, idempotency, locks, outbox, workflows | `reliability/` |
| Tracing, error monitoring, instrumentation | `observability/` |
| HTTP features (versioning, cookies, sessions, file upload, compression, SSE, webhooks) | `http/` |
| OpenAPI / Swagger | `openapi/` |
| GraphQL, WebSockets, microservices | `graphql/`, `websockets/`, `microservices/` |
| DI, dynamic modules, lifecycle, testing | `fundamentals/` |
| Nest CLI | `cli/` |

Examples: use `@nestjs/config` instead of reading `process.env` everywhere, `@nestjs/terminus` for health checks, `@nestjs/throttler` for rate limiting, `@nestjs/passport` for authentication, and `class-validator` with `ValidationPipe` for input validation.

## Always use the Nest CLI to create building blocks

**IMPORTANT: Never create NestJS building blocks by hand. Always generate them with the Nest CLI** (`pnpm exec nest generate <schematic> <name>`; the CLI is a dev dependency). The CLI creates files in the expected structure, adds spec files, and registers the new block in the right module.

Building blocks that must be generated with the CLI:

| Schematic | Command |
|---|---|
| application | `nest generate application <name>` |
| class | `nest generate class <name>` |
| configuration | `nest generate configuration` |
| controller | `nest generate controller <name>` |
| decorator | `nest generate decorator <name>` |
| filter | `nest generate filter <name>` |
| gateway | `nest generate gateway <name>` |
| guard | `nest generate guard <name>` |
| interceptor | `nest generate interceptor <name>` |
| interface | `nest generate interface <name>` |
| library | `nest generate library <name>` |
| middleware | `nest generate middleware <name>` |
| module | `nest generate module <name>` |
| pipe | `nest generate pipe <name>` |
| provider | `nest generate provider <name>` |
| resolver | `nest generate resolver <name>` |
| resource | `nest generate resource <name>` |
| service | `nest generate service <name>` |
| sub-app | `nest generate sub-app <name>` |

Guidelines:
- Run with `--dry-run` first when unsure what files will be created or changed.
- Generate first, then edit the generated files. Don't copy an existing file and rename it.
- Use `resource` to scaffold a full CRUD feature (module, controller, service, DTOs, entity) in one step.
- Keep the generated spec files and fill them in rather than deleting them.
- Use pnpm for everything: `pnpm exec` for installed binaries, `pnpm dlx` for tools that aren't installed, `pnpm add` to install. Never `npx` or `npm`.
